# Task: Configure `todo-ssr` DeploymentConfig with `ConfigMap` and `Pod Name` Environment Variable

- Create the ConfigMap `todo-ssr-config` containing the following details:

| Variable | Value |
|---|---|
| `CUSTOMER` | `blue` |
| `PRIORITY` | `gold` |

- Reconfigure the DeploymentConfig `todo-ssr` as follows:

1. Expose the data in the ConfigMap `todo-ssr-config` as environment variables.
2. Expose the `todo-ssr` Pod name as the `POD_NAME` environment variable.
3. Modify the DeploymentConfig to eliminate the need for future reconfigurations when adding resource variables.

---

## 📘 Understanding the Question

This task asks you to configure **one existing DeploymentConfig** by using **two different sources** for environment variables.


### 1️⃣ ConfigMap values

The ConfigMap must provide these variables to the application container:

```text
CUSTOMER=blue
PRIORITY=gold
```

The requirement about **future variables** is important. You must reference the **complete ConfigMap** by using `envFrom`, rather than selecting the current keys individually.

```yaml
envFrom:
  - configMapRef:
      name: todo-ssr-config
```

With this configuration, any additional valid key added later to `todo-ssr-config` becomes an environment variable in **newly created Pods**, without another DeploymentConfig edit.

### 2️⃣ Pod name

A Pod name is generated by OpenShift and can change whenever a new Pod is created. Therefore, you must not hard-code it.

Use the Kubernetes **Downward API** to read the current Pod's `metadata.name` field:

```yaml
env:
  - name: POD_NAME
    valueFrom:
      fieldRef:
        apiVersion: v1
        fieldPath: metadata.name
```

### 🧠 What each variable uses

| Environment variable | Source | Required YAML |
|---|---|---|
| `CUSTOMER` | ConfigMap | `envFrom.configMapRef` |
| `PRIORITY` | ConfigMap | `envFrom.configMapRef` |
| `POD_NAME` | Pod metadata | `env.valueFrom.fieldRef` |

# ✅ Solution

## 🔐 Step 1: Log in and select the project

The lab setup already logs in and creates the project. Confirm that you are working in the correct project:

```bash
oc project deploy-config
```

Verify the existing resources:

```bash
oc get deploymentconfig/todo-ssr
oc get pods
```

Expected result: the `todo-ssr` DeploymentConfig exists and has created an application Pod.

---

## 🗂️ Step 2: Create the ConfigMap

Create `todo-ssr-config` with both required entries:

```bash
oc create configmap todo-ssr-config \
  --from-literal=CUSTOMER=blue \
  --from-literal=PRIORITY=gold
```

Verify it:

```bash
oc get configmap/todo-ssr-config -o yaml
```

Expected relevant output:

```yaml
data:
  CUSTOMER: blue
  PRIORITY: gold
```

You can also use:

```bash
oc describe configmap/todo-ssr-config
```

### 💡 Explanation

`oc create configmap` creates a resource for non-sensitive application configuration. Each `--from-literal` option adds one key-value pair.

---

## 🔍 Step 3: Inspect the available YAML fields

Use the cluster's built-in API documentation instead of attempting to memorize every YAML branch devised by committee.

For `envFrom`:

```bash
oc explain deploymentconfig.spec.template.spec.containers.envFrom
```

For the Pod field reference:

```bash
oc explain deploymentconfig.spec.template.spec.containers.env.valueFrom.fieldRef
```

The second command shows that `metadata.name` is a supported value for `fieldPath`.

---

## 📦 Step 4: Identify the existing container name

A DeploymentConfig contains a Pod template, and the Pod template contains **one or more containers**. Check the actual container name:

```bash
oc get deploymentconfig/todo-ssr \
  -o jsonpath='{.spec.template.spec.containers[*].name}{"\n"}'
```
### Or 
```bash
oc get deploymentconfig/todo-ssr -o yaml | grep -A10 conainer
```

In our case, container name is `default-container`

Use the name returned by your cluster. Do not create a second container merely because the existing one did not introduce itself politely.

---

## ✏️ Step 5: Edit the DeploymentConfig from WebPortal. 

![img.png](img.png)

Add `envFrom` and `env` to that **same container**. The relevant section should resemble the following:

```yaml
spec:
  template:
    spec:
      containers:
        - name: default-container
          image: registry.ocp4.example.com:8443/redhattraining/hello-world-nginx:v1.0

          envFrom:
            - configMapRef:
                name: todo-ssr-config

          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  apiVersion: v1
                  fieldPath: metadata.name
```

> ⚠️ Replace `default-container` only when Step 4 reports a different container name. Keep all existing container fields, such as `image`, `resources`, `ports`, probes, and image pull settings.


### 💡 Explanation of `envFrom`

```yaml
envFrom:
  - configMapRef:
      name: todo-ssr-config
```

Read it as:

> Load all environment variables **from** the ConfigMap named `todo-ssr-config`.

The ConfigMap keys become variable names:

```text
CUSTOMER → CUSTOMER=blue
PRIORITY → PRIORITY=gold
```

Task : 2. Expose the `todo-ssr` Pod name as the `POD_NAME` environment variable.

### What we can do, we can check the already running pods' config and copy the syntax. 
```
oc get pods -A -oyaml | grep -C 5 valueFrom
```

### Take a reference from the output and add it.

```
      env:
      - name: POD_NAME
        valueFrom:
          fieldRef:
            apiVersion: v1
            fieldPath: metadata.name
```

## 🧪 Step 7: Validate the variables inside the running Pod

Store the newest running Pod in a shell variable:

```bash
POD=$(oc get pods \
  -l deploymentconfig=todo-ssr \
  --field-selector=status.phase=Running \
  --sort-by=.metadata.creationTimestamp \
  -o name | tail -1)
```

Display the selected Pod:

```bash
echo "$POD"
```

Validate the three required environment variables:

```bash
oc exec "$POD" -- printenv \
  | grep -E '^(CUSTOMER|PRIORITY|POD_NAME)=' \
  | sort
```

Expected output resembles:

```text
CUSTOMER=blue
POD_NAME=todo-ssr-2-7m9kx
PRIORITY=gold
```

The generated Pod name will differ.

### Confirm that `POD_NAME` matches the real Pod name

```bash
echo "Actual Pod name: ${POD#pod/}"
echo -n "POD_NAME value: "
oc exec "$POD" -- printenv POD_NAME
```

The two names must be identical.

# 🧪 Prove That Future ConfigMap Variables Do Not Require DeploymentConfig Reconfiguration

> ⚠️ Perform this section only in a practice lab. Do not add extra resources or values in a graded environment unless the task requests them.

## 1. Add a new ConfigMap key

```bash
oc set data configmap/todo-ssr-config REFERENCE=devops-wala
```

Verify the ConfigMap:

```bash
oc get configmap/todo-ssr-config -o yaml
```

Expected relevant section:

```yaml
data:
  CUSTOMER: blue
  PRIORITY: gold
  REFERENCE: devops-wala
```

## 2. Check the existing Pod

```bash
oc exec "$POD" -- printenv | grep '^REFERENCE='
```

Normally, this command produces no output. An existing container's environment is not rewritten when the ConfigMap changes.

## 3. Create a new Pod without editing the DeploymentConfig

```bash
oc rollout latest deploymentconfig/todo-ssr
oc rollout status deploymentconfig/todo-ssr
```

Obtain the new running Pod:

```bash
POD=$(oc get pods \
  -l deploymentconfig=todo-ssr \
  --field-selector=status.phase=Running \
  --sort-by=.metadata.creationTimestamp \
  -o name | tail -1)
```

Validate all four variables:

```bash
oc exec "$POD" -- printenv \
  | grep -E '^(CUSTOMER|PRIORITY|POD_NAME|REFERENCE)=' \
  | sort
```

Expected output resembles:

```text
CUSTOMER=blue
POD_NAME=todo-ssr-3-xxxxx
PRIORITY=gold
REFERENCE=devops-wala
```

✅ The new variable appears in the new Pod.

✅ The DeploymentConfig was **not edited again**.

This proves that `envFrom` satisfies the future-variable requirement.

### Optional cleanup

```bash
oc set data configmap/todo-ssr-config REFERENCE-
oc rollout latest deploymentconfig/todo-ssr
```

# 🧠 Memory Aids

## Remember `envFrom`

```text
All keys from a ConfigMap
          ↓
       envFrom
          ↓
    configMapRef
          ↓
         name
```

```yaml
envFrom:
  - configMapRef:
      name: todo-ssr-config
```

## Remember the Pod name structure

```text
POD_NAME
   ↓
valueFrom
   ↓
fieldRef
   ↓
fieldPath
   ↓
metadata.name
```

```yaml
env:
  - name: POD_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name
```

A useful sentence is:

> **`POD_NAME` gets its value from a Pod field reference whose field path is `metadata.name`.**

# ⚠️ Common Mistakes

| Mistake | Why it is wrong |
|---|---|
| Referencing the wrong ConfigMap name | The Pod cannot load `todo-ssr-config` if the YAML names another resource. |
| Configuring `CUSTOMER` and `PRIORITY` individually | Future ConfigMap keys would require another DeploymentConfig edit. |
| Hard-coding a Pod name | Pod names change during rollout and recreation. |
| Adding `env` under the wrong YAML level | `env` and `envFrom` belong to a container, not directly under the Pod spec. |
| Adding a second container accidentally | The variables must be added to the existing application container. |
| Expecting an existing Pod to receive new environment values | ConfigMap-backed environment variables are read when the container starts. |
| Using a copied Pod name in validation commands | Generated Pod names are temporary; discover the current Pod dynamically. |

# ✅ Final Answer Structure

The important part of the completed DeploymentConfig is:

```yaml
spec:
  template:
    spec:
      containers:
        - name: default-container
          envFrom:
            - configMapRef:
                name: todo-ssr-config
          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  apiVersion: v1
                  fieldPath: metadata.name
```

The running container must contain:

```text
CUSTOMER=blue
PRIORITY=gold
POD_NAME=<current-todo-ssr-pod-name>
```
